**Diagnóstico.** El prompt renderizado es el esperado (4 146 tokens: sistema del agente + entorno + bloque `# Tools` en formato Qwen + la tarea; `render_dump`). Lo que sí destaca: OpenCode no envía `temperature` ni `top_p` y el servidor usa por defecto **temperatura 1,0, sin `top_p`** —la peor configuración para una llamada a herramienta de un 7B—, mientras Qwen2.5-Coder recomienda 0,7/0,8. Siguiente experimento: la misma petición con temperaturas 0, 0,2, 0,7 y 1,0 (2 semillas) en una sola sesión del guest, aprovechando T81 (`temperaturas.sh`, `temperaturas.txt`).

**Experimentos con el prompt real (guest, una sesión persistente, T81 amortiza el prefill; `cola/`, `temperaturas.txt`).**
- Temperatura 0 / 0,2 / 0,7 / 1,0, 2 semillas cada una (8 muestras): **ninguna llamada a herramienta**; siempre «Entendido. Procederé a leer `TASK.md`…» o pide que se le pase el contenido (a 1,0 una dio `invalid_request`: intento mal formado). La temperatura no es la causa.
- Mensaje del usuario directo («Usa la herramienta `read` para leer /work/repo/TASK.md», 01 en español, 05 en inglés): el modelo **abre** una llamada, pero el servidor la rechaza: «llamada a herramienta truncada» (01, 05). «Empieza llamando a `read`… no expliques» (04): «argumentos que no son un objeto JSON».
- `tool_choice: required` y forzada a `read` (02, 03): «no hay llamada». El servidor **valida** `tool_choice` después de generar, no restringe la decodificación; no ayuda a que el modelo la escriba.

**Cuello de botella medido: no es QEMU.** La sonda `generar_crudo` (ejemplo nuevo de `soso-llm-api`, mismo runtime en el host con un solo hilo) también va a ~1 token/s en el prefill de 4 146 tokens: el prefill procesa token a token y lee los 4,8 GB de pesos por cada uno. Un prefill por lotes (cada fila de pesos se lee una vez y se multiplica por N vectores) lo reduciría de forma drástica; no existe todavía.
