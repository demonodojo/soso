# Seguimiento T45 — órdenes, capacidades y códigos de salida

## 2026-09-23 · intento 1

**Base:** commit `95de3c162` + diff sucio de la sesión.
**Por qué esta ficha:** T48 —la que desbloquea T14 y con ella SI-2— depende de
T45, y T45 tenía sus dos dependencias (T01, T02) cerradas y ninguna condición
de entrada. Así que era ésta, no T48.

### El problema, tal como estaba

Los dos frontends no sólo escribían distinto —`--clave valor` en el host,
posicional en el guest—; tenían **criterio distinto para el éxito**:

- guest `reconstruir`: imprimía «reconstrucción con N problema(s)» y devolvía
  `Ok(())`, es decir **exit 0**;
- guest `banco validar`: imprimía los problemas y devolvía **0**;
- guest `verificar protocolo`: imprimía el estado, incluso `fail`, y devolvía **0**;
- host `banco validar`: devolvía **1** donde su propia tabla documentada dice 2.

Un arnés que mire el código de salida —que es lo único que puede mirar sin
interpretar texto— daba por buena una medida rota. Eso es lo que NATIVO.md
apuntaba como «varias verificaciones imprimen fallo y devuelven `Ok(())`».

### Lo que se ha hecho

**`crates/soso-improve-core/src/cli.rs`** (nuevo, `no_std + alloc`):

- `Codigo`: 0 éxito, 1 no se pudo usar, 2 la medida falló, 3 captura
  inestable, 4 suite fallida. `Codigo::de_error` clasifica los errores del
  core, con `Inestable` aparte porque no es que la medida fallara, es que no se
  pudo medir.
- `Capacidad` / `Capacidades`: qué sabe hacer cada frontend de verdad, con la
  ficha que traerá lo que falta (T40 compilador, T41 cargo, T47 procesos).
  `exigir()` rechaza **antes del primer efecto**.
- `Orden`: orden serializable con nombre canónico, subcomando y argumentos con
  nombre. `parsear` acepta las dos sintaxis: con `--clave` y **posicional**,
  ésta con alias declarados por orden, no adivinados. Los alias de primer nivel
  del guest (`protocolo`, `programa`, `repo`) se normalizan a `verificar <sub>`.
- `Informe`: resultado comparable entre host y guest, con `schema_version`,
  código, número de problemas y JSON estable escrito a mano (el crate es
  `no_std`).
- `argv_de_texto`: argv por archivo, una línea por argumento, porque
  `split_whitespace` **no** conserva argv —una ruta con espacios se parte en
  dos— y el guest sólo recibe una cadena.

**`user/soso-improve`**: despacha por `cli::Orden`, comprueba la capacidad
antes de tocar nada, y las tres verificaciones devuelven ahora cuántos
problemas encontraron, de donde sale el código 2. Órdenes nuevas:
`capacidades` y `--orden-archivo <ruta>`.

**`tools/soso-improve`**: una sola pasada por el parser del core da el nombre
canónico y la capacidad; el host entiende ya la sintaxis posicional del guest
sin reescribir cada subcomando. `banco validar` pasa de 1 a **2**. La
clasificación de errores en `main` es la compartida.

**Fixtures CLI** en `rootfs/var/self-improvement/fixtures-cli/`: el caso Q04 con
su `esperado.json`, una respuesta correcta y una incorrecta. 1,4 KB, lo justo
para ejercitar éxito y fallo dentro del guest sin un banco entero.

### Pruebas

| Comprobación | Resultado |
|---|---|
| `cargo test -p soso-improve-core --features std` (11 pruebas nuevas de `cli`) | OK |
| `cargo test -p soso-improve-core -p soso-improve` | OK (57 en total) |
| `cargo build -p soso-improve-core --no-default-features` (C1: no_std) | OK |
| `cargo xtask test` — paso nuevo «soso-improve: órdenes y códigos de salida» | **OK en guest** |
| `cargo xtask check` | OK |

Las dos sintaxis dan la misma orden, comprobado en host y en prueba unitaria:

```sh
soso-improve banco listar --banco tests/self-improvement/cases   # idénticas
soso-improve banco listar tests/self-improvement/cases
soso-improve banco validar --banco /no/existe                    # rc=2, antes 1
```

El paso guest comprueba lo que motivó la ficha: `capacidades` publica lo que
hay, el caso Q04 correcto da `ok`, el **incorrecto sale con código 2**,
`verificar programa` se rechaza como capacidad ausente nombrando T40, y una
orden inventada se rechaza.

### Límites

- El host conserva su parser `Opciones` para los subcomandos; lo compartido es
  la orden canónica, la capacidad y el código. Unificar también el interior de
  cada subcomando no hacía falta para el objetivo de la ficha y habría tocado
  mucho más código del que el alcance permite.
- El transporte de `Orden` a un proceso es de **T47**, como dice la ficha; aquí
  sólo está el formato y el argv por archivo.
- `native_validation`: **partial**. Las órdenes y los códigos se ejecutan en
  guest, pero desde el arnés del host; repetirlo desde el runner nativo es T49.
