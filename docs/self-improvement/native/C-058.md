# C-058 — close de glibc cae en SYS_OPEN

**Estado:** hecha.

## Reproducción

Tras C-057, en el guest (`guest-rustc-emit-85.txt`) `rustc
--emit=obj` imprime:

```
rustc-LLVM ERROR: IO failure on output stream: File name too long
```

`guest-boot-85.txt`: el worker abre el objeto por la syscall 257
(`/tmp/t.t.942c5e9f45756909-cgu.0.rcgu.o`, 38 bytes, flags
`0x80241`). La ruta cabe en `PATH_MAX` (256) y el componente cabe
en `NAME_MAX` (255), así que ese `open` no es el `ENAMETOOLONG`.

Justo después entra `SYS_OPEN` con puntero `0x4` y longitud
`0x1006ab9140`. `0x4` es el descriptor que acaba de devolver el
`open`. `0x1006ab9140` es mayor que 4096, y `user_str` responde
`ENAMETOOLONG` (36). glibc `close` usa la syscall 3 de Linux; en
soso el 3 es `SYS_OPEN`, y `close` no rellena `rsi`, así que la
longitud es el valor que quedó en el registro. LLVM lo cuenta como
fallo del flujo de salida (`raw_fd_ostream` al cerrar).

El mismo arranque mata al pid 8 con un page fault de usuario en
`0x308`, `rip=0xbab2dd1` (`__libc_cleanup_push_defer`, lee
`%fs:0x10+0x308`). Ese hilo no tiene el TCB de glibc. Ocurre
después del `ENAMETOOLONG`.

## Qué se hizo

Si el primer argumento de la syscall 3 cabe en `MAX_FDS` (16), el
kernel lo atiende como `SYS_CLOSE`. Una ruta de soso no vive en
esas direcciones. `guest-rustc-emit-86.txt` ya no dice `File name
too long`: el objeto temporal se crea y el fallo siguiente es
copiarlo a `/tmp/t.o`. Eso es C-059, sin implementar. T40 no se
cierra.
